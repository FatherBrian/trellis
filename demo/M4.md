# M4 demo: Bring your own IdP

Ana signs in to her own IdP, report-bot trades her token for a grant, and one AuthZEN
endpoint answers any caller: an allow with a mask, or a deny that names the check.

## Run it

```bash
python -m pip install -e .
trellisd demo bring-your-own-idp
```

The demo starts an OIDC IdP and a Trellis server in-process and talks to both over HTTP,
as curl would. It then works through nine steps:

1. **Ana signs in to her IdP.** Trellis never sees her password, only the signed token.
2. **report-bot signs in as itself**, with client credentials. Its token names no person.
3. **report-bot trades both at Trellis's token endpoint** (RFC 8693, person as subject,
   agent as actor). Trellis checks Ana's token against her IdP's published keys, issuer,
   audience and expiry; finds her in the directory; and finds report-bot's client in the
   agent registry (`identities` in `agents.yaml`). The answer is a grant token for the
   Q3 close, which ends no later than Ana's own token.
4. **An AuthZEN call about the journal** is allowed, with `approver_email` masked and rows
   filtered to Ana's region.
5. **An AuthZEN call about payroll** is denied, naming the task scope.
6. **Trellis refuses** an agent not in the registry, Ana's token for another service, a
   token signed with a key her IdP never published, and an expired token. Each refusal is
   in the ledger.
7. **Downstream, as Ana.** For a server that takes the person's own token, Trellis exchanges
   Ana's token for one meant for `ledger-mcp` that still names her (Reef's `obo` mode in
   M5). The ledger records the exchange, never the token.
8. **Ana revokes the grant**, and the same call is denied at once.
9. **`trellisd trace`** shows Ana, report-bot, and the IdP that vouched for each.

## Against Keycloak

The demo realm in [examples/idp/keycloak](../examples/idp/keycloak) has Ana, Tom, three
agent clients and Trellis's own client, all with throwaway secrets.

```bash
docker run -d --name trellis-keycloak -p 8183:8080 \
    -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
    -e KC_HOSTNAME=http://localhost:8183 \
    -v "$PWD/examples/idp/keycloak:/opt/keycloak/data/import:ro" \
    keycloak/keycloak:26.4.0 start-dev --import-realm
trellisd demo bring-your-own-idp --keycloak http://localhost:8183/realms/trellis
```

This milestone was run against Keycloak 26.4 in a local container: password sign-in,
client credentials, and Keycloak's standard token exchange for the downstream token.
`TRELLISD_TEST_KEYCLOAK=http://localhost:8183/realms/trellis` adds that check to the tests.
Entra on-behalf-of is tested against the in-process IdP only, which speaks Entra's
request shape; it hasn't been run against Entra itself.

## Serve it yourself

```bash
export TRELLISD_CONFIG=examples/three-keys TRELLIS_IDP_SECRET=trellis-demo-secret
trellisd serve --port 8180

# Ana's token from Keycloak, report-bot's own, then a grant token from Trellis
ANA=$(curl -s http://localhost:8183/realms/trellis/protocol/openid-connect/token \
    -d grant_type=password -d client_id=trellis-cli -d username=ana -d password=ana-demo | jq -r .access_token)
BOT=$(curl -s http://localhost:8183/realms/trellis/protocol/openid-connect/token \
    -d grant_type=client_credentials -d client_id=report-bot \
    -d client_secret=report-bot-demo-secret | jq -r .access_token)
GRANT=$(curl -s http://localhost:8180/token \
    -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
    -d subject_token=$ANA -d actor_token=$BOT -d scope=finance -d task='Q3 close' | jq -r .access_token)

curl -s http://localhost:8180/access/v1/evaluation -H "Authorization: Bearer $GRANT" -d '{
  "subject":  {"type": "agent", "id": "report-bot"},
  "action":   {"name": "read"},
  "resource": {"type": "table", "id": "finance.gl.journal_entries"}}'
```

## The endpoints

- `POST /access/v1/evaluation`: AuthZEN 1.0. The grant token goes in the `Authorization`
  header (or `subject.properties.token`). The subject is the agent; a grant presented by
  another agent is denied. Columns go in `resource.properties.columns`. A malformed
  request is a 400; anything Trellis can't allow is `"decision": false` with a reason.
  `X-Request-ID` is echoed.
- `GET /.well-known/authzen-configuration`: discovery.
- `POST /token`: RFC 8693, Trellis as the broker. `scope` is the grant's tags and `task`
  says what it's for. A process agent sends only its own token, with `purpose` and
  `trigger_record`, to start a purpose run. Errors follow RFC 6749.

Every response's `context` carries `reason_admin` and, under `trellis`, Trellis's
obligations profile (`trellis-obligations-v1`): `obligations` (`mask`, column to reason,
and `row_filter`), `denied_by`, each check's answer, the contract and its version, and
`event_id`, the ledger entry written before the answer went out. The same code runs in
process (`trellisd.server.evaluate`), and a test checks the two return identical answers.

## Configuring an IdP

```yaml
idps:
  corp:
    issuer: https://login.microsoftonline.com/<tenant>/v2.0
    audience: api://trellis
    subject_claim: email          # must match a key under people
    exchange: entra-obo           # or rfc8693 for Keycloak, Okta, Ping; or none
    client_id: <trellis app id>
    client_secret_env: TRELLIS_IDP_SECRET
agents:
  report-bot:
    identities: [corp:<report-bot's client id>]
```

Trellis brokers sign-in: it never creates users or holds passwords. It keeps a person's
sign-in token in memory only, for downstream exchanges while their grant lives; after a
restart, the person signs in again before Trellis will act as them downstream.
