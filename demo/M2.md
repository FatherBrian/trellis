# M2 demo: Who allowed this?

The ledger answers "who allowed this?" for any call, and proves nobody has changed its
answer.

## Run it

```bash
python -m pip install -e .
trellisd demo who-allowed-this
```

It runs M1's Q3 close in a scratch database (the four calls, then ten routine queries),
and then:

1. **Traces the denied HR call.** `trellisd trace <event>` follows the decision to the
   grant it ran under, by the receipt the decision recorded: Ana let report-bot act for
   her on the Q3 close, at what time, with which scope, and the grant entry is signed.
   Then the three answers: Ana's access said yes (`access.ana-hr`), report-bot's ceiling
   said yes (`ceiling.report-bot`), and the task scope said no, because the grant's own
   policy covers only `finance`.
2. **Replays it.** `trellisd explain <event> --replay` re-runs the decision at the config
   and catalog snapshot it recorded (the same decision, check for check) and against
   today's policy (unchanged).
3. **Signs a checkpoint** of the head of the chain with the Ed25519 key.
4. **Covers someone's tracks.** Someone with database access rewrites the HR deny to say
   allowed, and deletes the last ten events.
5. **Verifies against the checkpoint.** `trellisd ledger verify --checkpoint` names both:
   the edited event, and the missing tail. Without the checkpoint, the cut tail would look
   like a shorter, valid chain.

```
$ trellisd ledger verify --checkpoint checkpoint.json
✗ the ledger fails verification against the checkpoint at event 15:
  ✗ event 4 was changed after it was written
  ✗ events 6 to 15 are missing from the end: the checkpoint signed at ... covers 15 events
```

## Step by step on your own database

```bash
export TRELLISD_CONFIG=examples/three-keys TRELLISD_DB=sqlite:///demo.db
export TRELLISD_KEY=trellisd-signing.key        # made on first use, mode 0600

trellisd grant issue --person ana@example.com --agent report-bot --task "Q3 close" \
    --scope finance --json
trellisd check --grant <grant-id> --json read hr.payroll     # note the event_id
trellisd trace <event-id>
trellisd explain <event-id> --replay
trellisd ledger checkpoint --out checkpoint.json
trellisd ledger verify --checkpoint checkpoint.json
trellisd ledger export --console                 # one OpenTelemetry span per event
```

`trellisd ledger export` without `--console` sends spans over OTLP (install the `otel`
extra and set `OTEL_EXPORTER_OTLP_ENDPOINT`). Events wait in an outbox written in the same
transaction as the event; export is at least once and idempotent on the event id, and a
collector outage never blocks a decision.

## What's in the ledger now

- **Grant receipts.** Issue, refusal and revocation are signed ledger entries; a grant's
  receipt is the hash of its issue entry.
- **Every decision** records the grant's receipt, all three answers, the Cedar policy ids
  behind each (and the policies each check considered), the config version and the
  catalog snapshot it ran against, so it can be replayed.
- **Ledger before the door opens.** A failed write raises `LedgerUnavailable`; the call is
  denied and a guarded tool never runs.
- **SQLite and Postgres** pass one shared test suite; appends to the one chain are
  serialized (an exclusive table lock on Postgres).

## Tests

```bash
pytest                                                    # SQLite
TRELLISD_TEST_POSTGRES=postgresql://user:pass@localhost:5432/db pytest   # both
```

They cover an edited row and a cut tail failing against a checkpoint, a history rewritten
with fresh hashes, a forged signature or checkpoint, a failed write that denies with the
tool never running, every decision linking to an existing grant entry, replay reproducing
each kind of decision, and a sink outage that leaves events queued without blocking.
