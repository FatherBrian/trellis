# M1 demo: Three keys

Every call an agent makes needs three yeses, asked separately in Cedar:

- **the person's access**: what Ana herself may read;
- **the agent's ceiling**: the most report-bot may ever touch, set by its owner;
- **the task scope**: what this grant covers ("Q3 close", tag `finance`).

A process agent gets the same three checks, with a **purpose** (which has a named human
owner) and a **trigger** (the one record that started the run) in place of the person and
the task.

## Run it

```bash
python -m pip install -e .          # installs the trellisd command
trellisd demo three-keys
```

It uses a scratch SQLite database, so it starts clean every time. Pass
`--keep --db sqlite:///demo.db` (or a `postgresql://` URL) to keep the grants and the ledger.

## What you see

```
CALL                                  Ana's access  report-bot's ceiling  the task         RESULT
read finance.gl.journal_entries            ✓                 ✓               ✓      ALLOW  masked approver_email; rows region = 'emea'
read finance.gl.export_ledger              ✓                 ✗               ✓      DENY   it may never touch export_controlled
read hr.payroll                            ✓                 ✓               ✗      DENY   the grant covers finance, and hr.payroll is hr, pii
read finance.treasury.cash_positions       ✗                 ✓               ✓      DENY   no access rule lets ana@example.com read ...
```

1. The journal is allowed. `approver_email` is masked by the `@mask("pii")` annotation on
   the access rule that decided, and the `@row_filter` keeps Ana's own region.
2. The export ledger: Ana can read it and the task covers finance, but report-bot's
   ceiling says never `export_controlled`. Only the ceiling says no.
3. Payroll: Ana can read HR and report-bot's ceiling includes HR, but this grant is for
   the Q3 close. Only the task says no.
4. Treasury: the bot and the task would allow it, but Ana can't read treasury herself, so
   she can't hand it on. Only Ana's access says no.

Then: Ana tries to widen the grant to `export_controlled` and is refused at issue; an
inspection record starts a run of inspector-bot under the `inspection-review` purpose,
whose rows are bound to that record and whose ceiling masks the inspector's email, while
the same run asking for the journal gets three crosses; Ana revokes report-bot's grant and
its next call fails the task check. The ledger then verifies: every grant, refusal,
revocation and decision is hash-chained, and each decision records all three answers and
the Cedar policies behind them.

## Step by step

```bash
export TRELLISD_CONFIG=examples/three-keys TRELLISD_DB=sqlite:///demo.db

trellisd validate                     # YAML checks and the Cedar validates
trellisd compile                      # the Cedar Trellis generates
trellisd grant issue --person ana@example.com --agent report-bot \
    --task "Q3 close" --scope finance
trellisd check --grant <grant-id> read hr.payroll
trellisd grant run --purpose inspection-review --agent inspector-bot \
    --record INS-1042 --by quality-lead@example.com
trellisd grant list
trellisd grant revoke <grant-id> --by ana@example.com
trellisd trace
trellisd ledger verify
```

## Tests

```bash
pytest                                             # SQLite
TRELLISD_TEST_POSTGRES=postgresql://user:pass@localhost:5432/db pytest -m postgres
```

The tests include golden YAML-to-Cedar output, the four calls above, purpose runs, and two
Hypothesis properties: a call is allowed exactly when all three checks allow it, and a
permit written for one limit never satisfies another.
