# M6 demo: The whole story in one command

`docker compose up` in [quickstart/](../quickstart) starts Postgres, an Iceberg REST
catalog with a seeded table, Keycloak, two MCP servers, Trellis with Reef in front of the
servers, and a scripted agent. The agent asks Reef for tools and sees only its grant's,
reads a masked result, is denied a tool outside its task, and then traces the deny to the
check that said no, the grant, and who allowed it. Nothing is faked: the tokens are
Keycloak's, the pii tag is the catalog's, and the ledger is in Postgres.

## Run it

```bash
cd quickstart
docker compose up --build
```

Then Ctrl+C and `docker compose down -v`. CI runs the same thing from scratch (the
`quickstart` job): `docker compose up --build --detach --wait trellis`, then the agent
twice; the agent exits non-zero if any check fails. `pytest reef/tests/test_quickstart.py`
runs the same agent against an in-process IdP and catalog, no Docker needed.

## What it shows

```

   grant g-8af90ef666: report-bot for ana@example.com, task 'Q3 close', scope finance

2. report-bot connects to Reef with its grant token and lists its tools:
   ledger_journal_entries: Posted journal entries, one row per line.
     Through Reef for ana@example.com (Q3 close): only rows where region = 'emea'; approver_email comes back as ***.
   ✓ only its grant's tool is listed

3. It reads the journal:
   {"entry_id": "JE-1001", "amount": 1250.0, "region": "emea", "approver_email": "***"}
   {"entry_id": "JE-1003", "amount": 980.0, "region": "emea", "approver_email": "***"}
   ✓ two rows: Ana's region only
   ✓ approver_email is masked
   approver_email is pii because catalog lakehouse says so
   ✓ the pii tag came from the catalog

   ✓ forwarded as Ana (obo)

   Denied at the door: denied by the task scope: the grant covers finance, and mcp://hr/payroll is confidential, hr. ana@example.com would have to give report-bot a grant whose task covers hr.
```

## What's worth noticing

- **Ana could read payroll; her grant couldn't.** The person check and the ceiling both
  said yes. The task scope is the one that said no, and the trace names it. That's the
  grant paradigm: an agent's access is the intersection of three keys, not its owner's
  access.
- **The mask came from the catalog.** The contract lists `approver_email` with no tags. A
  steward tagged it pii in Iceberg, and the trace of the read says so, with the
  catalog's metadata version.
- **Ana's own token reached the ledger server.** Reef asked Trellis for an obo token;
  Trellis exchanged Ana's held sign-in at Keycloak for audience `ledger-mcp`. The server
  checked Keycloak's signature itself.
- **The deny forwarded nothing.** The blocked enforcement event is in the ledger before
  the agent sees the error, and the hr server's log is empty.

## How it's put together

- One image (the repo's [Dockerfile](../Dockerfile)) has `trellisd` and `reef`.
- `reef serve --trellis-port 8180` runs Trellis's HTTP endpoints in Reef's process. The
  person's sign-in, needed for obo mode, is held in memory and never written down, so the
  token endpoint and the door have to share it.
- `reef sample ledger|hr` runs the sample servers; `reef quickstart seed` writes the
  table and its tag through the Iceberg REST API; `reef quickstart agent` is the agent.
- The MCP SDK checks Host headers when bound to a loopback address (DNS rebinding
  protection). Inside the compose network the servers bind `0.0.0.0`, so they answer to
  their service names.
